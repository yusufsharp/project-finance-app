# Выступление на 4 минуты

Участники: Файзуллин Марат, Шарыпов Юсуф. Основная часть — слайды 1–8. Слайды 9–30 — приложение с доказательствами, которое открывается по запросу. Оба участника должны понимать весь проект и уметь выполнить каждый сценарий из ручного чек-листа.

## Марат, 0:00–2:00

**Слайд 1, 0:00–0:15.** Мы сделали «Копилку», приложение для учёта личных финансов. Пользователь записывает доходы и расходы, видит баланс и распределение расходов по категориям. Работаем вдвоём: Файзуллин Марат и Шарыпов Юсуф.

**Слайд 2, 0:15–0:50.** Здесь работает настоящий интерфейс. Добавим тестовый расход, изменим сумму и удалим запись. После перезагрузки данные сохраняются, потому что операции хранятся в PostgreSQL. Есть поиск, фильтр доходов и расходов, выбор периода. Баланс — это записанные доходы минус расходы. Начального остатка и отдельных пользователей пока нет.

**Слайд 3, 0:50–1:25.** Frontend работает отдельным сервисом nginx, backend — operations на Python. Notifications — отдельный consumer, который получает событие создания и записывает уведомление в журнал. База и брокер имеют по три узла. Два HAProxy дают приложениям постоянные адреса подключения. Patroni выбирает primary с помощью etcd. Redis ускоряет чтение по UUID. Есть отдельный сервис резервного копирования. Всё запускается через Docker Compose.

**Слайд 4, 1:25–2:00.** В API есть создание, чтение, изменение и удаление. Схема и миграция лежат в SQL-файле. Первое чтение операции идёт в БД, повторное — в Redis, что видно по заголовку ответа. Кэш живёт 300 секунд и сбрасывается при изменении или удалении. Операция и событие создания попадают в одну транзакцию через outbox. Publisher удаляет событие только после подтверждения RabbitMQ. Consumer подтверждает обработку. Повторная доставка возможна.

## Юсуф, 2:00–4:00

**Слайд 5, 2:00–2:35.** У нас четыре сегмента: edge для HTTP, data для хранилищ, messaging для событий и control для etcd/Patroni. Notifications может подключаться только к брокеру. Firewall запрещает остальное, приложения работают от nobody без эффективных capabilities. Одинаковое TCP-подключение из operations проходит, из notifications к БД отклоняется. При временном запрете нужного соединения backend с БД запрос получает 503. После удаления правила снова 200.

**Слайд 6, 2:35–3:10.** Для проверки отказоустойчивости мы отправили SIGKILL текущему primary PostgreSQL и лидеру quorum-очереди RabbitMQ, предварительно отключив их автоматический restart. БД выбрала другой primary за 20,9 секунды. Новая запись прошла, старая сохранилась и прочиталась мимо Redis. Брокер восстановил доставку за 9 секунд. Consumer получил и подтверждённое до аварии сообщение, и новое. Затем мы вернули узлы.

**Слайд 7, 3:10–3:40.** Ежедневно создаётся pg_dump, сохраняются семь успешных копий и SHA-256. Мы восстановили копию в новую БД отдельного инстанса за 4,1 секунды с учётом его запуска. Все поля 21 операции совпали. Цель SLO — 99,9% валидных запросов за 30 суток, но статистику пока не собираем. MTBF — тоже цель. Весь кластер находится на одном ноутбуке, его отказ не покрывается.

**Слайд 8, 3:40–4:00.** Запуск начинается с `python3 scripts/start_hw5.py`, затем приложение доступно на localhost:8080. В репозитории есть код, презентация, ручной чек-лист и архив без секретов. Подробные скриншоты всех минимальных сценариев находятся в приложении к презентации. Публичного адреса приложения нет, показ выполняем локально.

## Подготовка живого показа

1. Заранее запустите Docker и `docker compose up --build -d --wait`. Подготовьте окно терминала в корне репозитория и страницу http://127.0.0.1:8080/.
2. Показывайте сборку и деплой короткой повторной командой либо сохранённым реальным журналом сборки; преподавателю должна быть понятна сама процедура.
3. Создавайте и удаляйте только свои тестовые операции. Сценарии CRUD описаны в пунктах 2–7 ручного чек-листа.
4. Если преподаватель просит конкретную проверку, откройте соответствующий слайд из таблицы на слайде 9 и выполните команды из `docs/MANUAL_CHECKS.md`. HA-сценарии дольше одного обычного запроса, их время заложите отдельно.
5. После блокировок/аварий возвращайте правила, контейнеры, restart policy и consumer. В конце покажите здоровый стенд.
6. Перед отправкой проверьте доступ к исходникам без своей авторизации или дайте доступную ссылку на ZIP. Текущий анонимный ответ GitHub API — 404. Не называйте репозиторий публичным без проверки.

## Ответы на вероятные вопросы

- **Почему notifications отдельно?** Выполняет независимое действие и читает сообщения из брокера, не получая доступ к БД и кэшу.
- **Почему outbox?** Операция и намерение отправить событие сохраняются атомарно. При недоступном брокере publisher повторяет отправку позже.
- **Где exactly-once?** Его не заявляем: повтор после неопределённого подтверждения допустим. У POST пока нет Idempotency-Key.
- **Почему после DELETE ещё может прийти событие?** Это независимый снимок создания. Удаление операции не отменяет уже сохранённое событие.
- **Что делает HAProxy для БД?** Проверяет Patroni `/primary` и направляет новые подключения на действующий primary.
- **Зачем etcd?** Хранит состояние и лидерский ключ, помогает Patroni избежать двух primary при доступном кворуме.
- **Что при потере большинства?** Запись может остановиться. Доступность кворума и synchronous standby важнее обещания записи при любом отказе.
- **Почему backup, если есть реплики?** Репликация переносит и логическое удаление данных. Копия даёт отдельную точку восстановления.
- **Чем RTO отличается от MTTR?** RTO — целевое время восстановления сценария, MTTR — среднее по серии инцидентов. Один удачный тест не доказывает среднее.
- **Достигнут ли SLO?** Нет непрерывного SLI за месяц. Число 99,9% является целевым, а не измеренным SLA.
