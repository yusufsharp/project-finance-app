# Трекер личных финансов

Групповой учебный проект по архитектуре высоконагруженных систем. Мы проектируем приложение, в котором пользователь ведёт доходы и расходы, задаёт бюджеты по категориям и следит за стоимостью портфеля.

Сейчас есть веб-интерфейс «Копилка»: доходы и расходы, баланс, категории, поиск, фильтры и полный CRUD операций. Приложение сохраняет данные в PostgreSQL, кэширует чтение и отправляет событие создания отдельному consumer. Уведомление демонстрируется записью в журнале. Бюджеты и портфель пока описаны как развитие предметной области.

## ДЗ 2. Запуск стенда

Потребуются Docker Engine на Linux или Docker Desktop, Compose 2.33.1+, Python 3 на хосте, свободный порт 8080 и примерно 8 ГБ памяти для Docker. Firewall внутри контейнеров требует поддержку `NET_ADMIN` и iptables. Выполняйте команды из корня репозитория.

Текущая версия включает HA-компоненты ДЗ 5. Для первого запуска или переноса старого стенда выполните:

```sh
python3 scripts/start_hw5.py
```

Скрипт создаёт недостающие секреты в `.env`, собирает образы и запускает стенд. Если обнаружена старая БД ДЗ 4, он останавливает прикладные сервисы, сохраняет dump и переносит операции в новый кластер с проверкой количества. Старые тома сохраняются. При ненулевой очереди старого брокера перенос прерывается, чтобы не потерять события.

Для последующих запусков с уже подготовленной `.env`:

```sh
docker compose up --build -d --wait
docker compose ps
curl -fsS http://127.0.0.1:8080/
```

В текущей версии работают 16 основных сервисов: frontend, operations, notifications, Redis, три PostgreSQL/Patroni, три etcd, три RabbitMQ, два HAProxy и db-backup. `db` и `broker` теперь обозначают стабильные адреса HAProxy, а не одиночные инфраструктурные узлы. Дополнительный db-restore запускается только для восстановления. Откройте http://127.0.0.1:8080/ — там работает веб-интерфейс. Hello-world API сохранён по `/api`. Для проверки:

```sh
docker compose exec db-backup psql -h db -U finance -d finance -c 'SELECT 1;'
docker compose exec cache redis-cli ping
docker compose exec rabbit1 rabbitmq-diagnostics -q ping
docker compose exec pg1 patronictl -c /etc/patroni.yml list
```

Остановить стенд можно командой `docker compose down`. Данные PostgreSQL, etcd и RabbitMQ остаются в именованных томах. `backups/` хранит резервные копии на хосте. Исходная конфигурация до ДЗ 5 сохранена как `docker-compose.hw4.yml`; старые тома `db-data` и `broker-data` не удалялись.

## ДЗ 3. Запись операции, кэш и события

Соберите обновлённый стенд командой `docker compose up --build -d --wait`.

Создайте расход:

```sh
curl -i -X POST http://127.0.0.1:8080/operations \
  -H 'Content-Type: application/json' \
  -d '{"amount":"450.50","category":"Продукты"}'
```

Ожидается HTTP 201 с UUID в поле `id`. Подставьте этот UUID вместо `ID` в следующие команды:

```sh
curl -i http://127.0.0.1:8080/operations/ID
curl -i http://127.0.0.1:8080/operations/ID
docker compose exec db-backup psql -h db -U finance -d finance -c 'SELECT * FROM operations;'
docker compose exec cache redis-cli GET operation:ID
docker compose logs operations notifications
```

Первый GET возвращает заголовок `X-Data-Source: database` и заполняет Redis. Повторный GET возвращает `X-Data-Source: cache`. Кэш хранится 300 секунд. POST сбрасывает ключ новой операции. Несуществующая операция возвращает 404, некорректная сумма или категория — 400. Сумма должна быть положительной, меньше триллиона и содержать до двух знаков после запятой.

Операция и событие записываются одной транзакцией в таблицы `operations` и `outbox`. Фоновый обработчик operations публикует событие в quorum-очередь RabbitMQ `operation.created` с тремя репликами, получает подтверждение брокера и удаляет запись из outbox. Отдельный сервис notifications читает сообщения, записывает их в журнал и подтверждает обработку. В журнале operations ищите `Published operation.created`, в notifications — `Consumed operation.created` с UUID созданного расхода. Уведомление пока демонстрируется записью в журнале.

При временной недоступности брокера события остаются в outbox и отправляются после восстановления соединения. Доставка допускает повторения. При сбое Redis чтение выполняется из PostgreSQL. Для демонстрации используется один экземпляр сервиса с фоновым обработчиком. Повторный POST создаёт новую операцию.

## ДЗ 4. Сегментация сети и Firewall

Frontend подключён только к `edge` и проксирует HTTP к operations. Созданы сети `edge`, `data`, `messaging` (и внутренняя `control` для HA). Operations может обращаться к PostgreSQL, Redis и RabbitMQ; notifications — только к RabbitMQ. Доступ notifications к БД и кэшу явно запрещён iptables. Приложения работают от nobody после установки правил Firewall.

После запуска стенда выполните интеграционную проверку (нужен Python 3 на хосте):

```sh
python3 scripts/verify_hw4.py
```

Проверка создаёт один демонстрационный расход. Она показывает разрешения и запреты, рост счётчиков REJECT, чтение из БД/кэша и получение события сервисом notifications.

## ДЗ 5. Надёжность, переключение и резервное копирование

PostgreSQL использует Patroni, три узла etcd и синхронную реплику. При аварии primary Patroni выбирает новый primary, а HAProxy направляет к нему запросы. RabbitMQ состоит из трёх узлов с quorum-очередью и автоматически выбирает нового лидера. Redis восстанавливается перезапуском, при его сбое API читает из БД. Прикладные процессы и прокси имеют `restart: unless-stopped`.

Полная проверка на локальном демонстрационном стенде:

```sh
python3 scripts/verify_hw5.py
```

Скрипт создаёт тестовые расходы, аварийно останавливает текущих лидеров PostgreSQL и RabbitMQ, проверяет чтение из БД, доставку подтверждённого сообщения и новых событий, затем возвращает узлы. После этого создаёт backup и восстанавливает его в новую БД отдельного db-restore. Исходную БД и её тома он не удаляет. Результаты: `output/hw5/report.json`.

Резервное копирование идёт ежедневно, хранит семь последних копий и SHA-256. При ошибке повторяется через 30 секунд. Ручной backup и отдельное восстановление:

```sh
docker compose exec db-backup sh /backup/backup-once.sh
python3 scripts/restore_hw5.py backups/finance-ИМЯ-КОПИИ.dump
```

## Веб-интерфейс

Откройте **http://127.0.0.1:8080/** после запуска Compose. Отдельный сервис `frontend` (nginx, HTML/CSS/JavaScript без внешних CDN) обслуживает страницу и проксирует API в operations. У backend больше нет опубликованного порта; frontend не подключён к data/messaging/control.

- Обзор: баланс (доходы минус расходы), сводка за всё время/текущий месяц/30 дней, распределение расходов по категориям.
- История: поиск категории, фильтр типа, страницы по 8 записей. Фильтры меняют историю; сводка и категории отражают весь выбранный период.
- Добавление дохода или расхода, редактирование суммы/категории/типа, удаление с подтверждением. Дата создания сохраняется при редактировании.
- Ошибка загрузки показывает сообщение и кнопку повтора; уже загруженные данные остаются на экране с пометкой об устаревании.

Существующие операции автоматически получают тип `expense`. Скрипт схемы и миграции: [operations/sql/schema.sql](operations/sql/schema.sql). API совместим со старыми POST без `kind`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/operations` | Все операции, новые сначала, `{"operations": [...]}` |
| POST | `/operations` | Создание: `amount`, `category`, `kind` (`expense` по умолчанию) |
| GET | `/operations/UUID` | Чтение с Redis-кэшем и заголовком `X-Data-Source` |
| PUT | `/operations/UUID` | Полная замена суммы/категории/типа, инвалидация кэша |
| DELETE | `/operations/UUID` | Удаление операции и инвалидация кэша |
| GET | `/health/ready` | Готовность API и БД |
| GET | `/api` | Hello-world backend |

В outbox хранится независимый снимок события создания. Если операция изменена или удалена до доставки, исходное событие всё равно доставляется; новые события update/delete не публикуются.

Проверка веб-сервиса и CRUD: `python3 scripts/verify_frontend.py`. Она проверяет валидацию, чтение из кэша, свежие данные после PUT и 404 после DELETE; временная запись очищается. Интерфейс также проверен вручную в браузере, включая мобильную ширину 390 px.

Это локальное общее пространство без авторизации, отдельных пользователей и начального остатка; баланс считается по записанным операциям. История загружается целиком и фильтруется в браузере — для больших объёмов понадобятся серверная пагинация и агрегации.

## Подготовка материалов защиты

Актуальная презентация находится в `defense/`, ранняя `output/defense/` описывает старую архитектуру. В новой версии 8 слайдов основного выступления и 22 слайда доказательств этапов 1–5. Подробности и результаты: [defense/README.md](defense/README.md).

Дополнительная проверка обязательного сценария firewall:

```sh
python3 scripts/verify_firewall_outage.py
```

Она временно блокирует operations → db, проверяет HTTP 503 и счётчик правила, удаляет временный запрет в finally и подтверждает восстановление HTTP 200. Применяется к локальному учебному стенду.

Архив без `.env`, данных, резервных копий и учебных PDF: `python3 scripts/package_source.py`.
